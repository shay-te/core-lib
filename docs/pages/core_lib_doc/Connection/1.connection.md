A *connection* is how a `DataAccess` class reaches a data source: a SQL database, MongoDB, Solr, Neo4j, Elasticsearch, or any object you wrap yourself. Core-Lib does not hide the native client. It gives every data source the same three steps:

1. `CoreLib.__init__` builds a **connection factory** from config.
2. It passes the factory to a `DataAccess`.
3. The `DataAccess` opens a block with `with factory.get() as client:` and uses the native client inside it (a SQLAlchemy session, a `MongoClient`, a `pysolr.Solr`, and so on).

What happens when the block exits depends on the data source (see the table below). For SQLAlchemy the wrapper also handles the session (commit, rollback, close), and for Neo4j it closes the session; for MongoDB, Solr and Elasticsearch it only hands you the client. [Why not use the driver directly?](#why-not-use-the-driver-directly) says what it adds.

> **Where it fits:** Connection layer. `CoreLib.__init__` builds the factories and passes them to `DataAccess` classes. `Service` classes never see them.

> Unfamiliar with terms like "context manager" or "session"? See the [Glossary](glossary.html).

## Built-in connections

| Data source | Factory | `with factory.get() as x:` gives you | When the block exits |
|---|---|---|---|
| [SQL databases](sql_alchemy_connection.html) | `SqlAlchemyConnectionFactory` | a new [SQLAlchemy](https://docs.sqlalchemy.org/en/20/orm/session.html){:target="_blank"} `Session` | commits and closes the session; if your code raised, rolls back first |
| [MongoDB](mongodb_connection_factory.html) | `MongoDBConnectionFactory` | the factory's [PyMongo](https://pymongo.readthedocs.io/en/stable/){:target="_blank"} `MongoClient` | nothing |
| [Solr](solr_connection_factory.html) | `SolrConnectionFactory` | the factory's [pysolr](https://github.com/django-haystack/pysolr/){:target="_blank"} `Solr` client | nothing |
| [Neo4j](neo4j_connection_factory.html) | `Neo4jConnectionFactory` | a new [neo4j](https://github.com/neo4j/neo4j-python-driver){:target="_blank"} `Session` | closes the session |
| [Elasticsearch](elasticsearch_connection_factory.html) | `ElasticSearchConnectionFactory` | the factory's [elasticsearch-py](https://www.elastic.co/guide/en/elasticsearch/client/python-api/current/index.html){:target="_blank"} `Elasticsearch` client | nothing |
| [Any object](object_connection_factory.html) | `ObjectConnectionFactory` | your object, or what your open callback returns | calls your close callback, if you gave one |

`pip install core-lib` installs the client libraries for all of these except Elasticsearch. For Elasticsearch, also install `elasticsearch` (see [its page](elasticsearch_connection_factory.html)).

## Why not use the driver directly?

You can. A `DataAccess` may hold a `MongoClient` or a `pysolr.Solr` itself, and for MongoDB, Solr and Elasticsearch the wrapper adds little. What it does add:

1. **Built from config.** The connection is created from YAML, so tests and production run the same code with a different config: SQLite instead of Postgres, a local Solr core, or another `_target_` class.
2. **One shared connection per process**, if you build a `_target_` block with `get_or_reg` ([below](#sharing-a-connection-between-core-libs)).
3. **Easy to replace in a test.** A `DataAccess` only calls `factory.get()`, so a unit test can pass it an `ObjectConnectionFactory` that wraps a fake or an in-memory client. The [MongoDB page](mongodb_connection_factory.html#testing-without-a-server) shows this with `mongomock`.
4. **Session handling for SQLAlchemy and Neo4j.** SQLAlchemy sessions are committed and closed for you; if your code raises inside the block, the session is rolled back first. Neo4j sessions are closed.

For MongoDB, Solr and Elasticsearch only points 1 to 3 apply: the `with` block hands you the factory's client and does nothing on exit. If you don't need those three things, using the client directly is fine.

## How a connection is configured

Every factory except `ObjectConnectionFactory` takes one config node in `__init__`. That node holds a `url:` block, plus the few keys some factories need: `session` settings for SQLAlchemy, `always_commit` for Solr, `credentials` for Neo4j.

The `url:` block becomes a URL string through `build_url`:

```text
protocol://username:password@host:port/path/file
```

Every part is optional and is left out when it is empty. `build_url` does not escape anything, so a username or password that contains `@`, `:` or `/` must be percent-encoded first (for example with `urllib.parse.quote_plus`).

Most pages put that node under `config:`, in a block whose `_target_` names the factory class:

```yaml
core_lib:
  data:
    mongodb:
      _target_: core_lib.connection.mongodb_connection_factory.MongoDBConnectionFactory
      config:
        url:
          protocol: mongodb
          host: localhost
          port: 27017
```

In `CoreLib.__init__` you build that block in one of three ways. Pick one:

| Call | What it does |
|---|---|
| `instantiate_config(config.core_lib.data.mongodb)` | Builds the `_target_` class and passes it `config`. A test config can point `_target_` at another class. See [Instantiate Config](instantiate_config.html). |
| `MongoDBConnectionFactory(config.core_lib.data.mongodb.config)` | The same thing by hand. Pass the inner `config` node, not the whole block. |
| `CoreLib.connection_factory_registry.get_or_reg(config.core_lib.data.mongodb)` | Builds the factory once per process and shares it. Needs an `_instance_key_` in the block ([below](#sharing-a-connection-between-core-libs)). The SQLAlchemy page uses this. |

Solr is the one exception. Core-Lib's packaged defaults already declare `core_lib.data.solr` as a node without `_target_` (`always_commit: true`, `url: ~`), so the [Solr page](solr_connection_factory.html) fills in that node and calls the constructor.

## Sharing a connection between Core-Libs

*core_lib.connection.connection_factory_registry.ConnectionFactoryRegistry* [[source]](https://github.com/shay-te/core-lib/blob/master/core_lib/connection/connection_factory_registry.py){:target="_blank"}

`CoreLib.connection_factory_registry` is one registry for the whole process. Its `get_or_reg(block)` builds the factory from a `_target_` block the first time, stores it under the block's `_instance_key_`, and returns that same factory on every later call with that key. So when several Core-Libs in one process use the same database, they share one engine and connection pool instead of each opening its own.

Core-Lib's packaged defaults set `_instance_key_: sqlalchemy_connection` on `core_lib.data.sqlalchemy`, so this is how you build the SQL connection:

```python
db = CoreLib.connection_factory_registry.get_or_reg(self.config.core_lib.data.sqlalchemy)
```

- The key alone decides what is shared. A second block with the same `_instance_key_` gets the first factory, even if its URL is different. Give each database its own key.
- Without `_instance_key_`, `get_or_reg` logs a warning and builds a new factory on every call, like `instantiate_config`.
- A block that has an `_instance_key_` must be built with `get_or_reg`. `instantiate_config` passes the key on to the factory as an argument, and the factory rejects it.

See [Registry](registry.html#connection-factory-registry) for the full reference.

## The Connection base class

*core_lib.connection.connection.Connection* [[source]](https://github.com/shay-te/core-lib/blob/master/core_lib/connection/connection.py){:target="_blank"}

`Connection` is an abstract base class. It only declares `__enter__` and `__exit__`; each concrete connection implements them as the table above describes, so every connection works in a `with` statement. A factory's `get()` returns a `Connection`.

To support another kind of data source, subclass `ConnectionFactory` (its one method is `get()`) and `Connection`, or wrap your client in an [`ObjectConnectionFactory`](object_connection_factory.html).
