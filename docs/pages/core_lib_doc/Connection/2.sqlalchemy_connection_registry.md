Every unit of database work needs the same code around it: open a session, commit, roll back if something failed, close. `SqlAlchemyConnectionFactory` builds the SQLAlchemy engine (and its connection pool) from config, and does that session work for you in `with db.get() as session:`. Inside the block you write normal SQLAlchemy.

**What it adds over plain SQLAlchemy:** the engine is built from config, each `with` block gets its own session, the session is committed and closed on exit, and it is rolled back if your code raises. That is a small wrapper; you could write the same with `sessionmaker` and a context manager of your own. You use this one because the [CRUD base classes](crud.html) take it, and [migrations](alembic.html) read the same config.

> **Where it fits:** Connection layer for relational databases. Build it in `CoreLib.__init__`, pass it to your `DataAccess` classes, and keep sessions out of `Service` code.

## Example

### `your_core_lib.yaml`

{% raw %}
```yaml
# @package _global_
core_lib:
  data:
    sqlalchemy:
      _instance_key_: sqlalchemy_connection
      _target_: core_lib.connection.sql_alchemy_connection_factory.SqlAlchemyConnectionFactory
      config:
        log_queries: false
        create_db: false
        session:
          pool_recycle: 3600
          pool_pre_ping: false
        url:
          protocol: postgresql
          username: ${oc.env:POSTGRES_USER}
          password: ${oc.env:POSTGRES_PASSWORD}
          host: ${oc.env:POSTGRES_HOST}
          port: ${oc.decode:${oc.env:POSTGRES_PORT,5432}}
          file: ${oc.env:POSTGRES_DB}
```
{% endraw %}

Keep this block at `core_lib.data.sqlalchemy`, in this shape (`_target_` plus `config:`). It is the same path and shape as Core-Lib's packaged defaults, and [Alembic](alembic.html) reads the database URL from `core_lib.data.sqlalchemy.config.url`. If you put the keys directly under `sqlalchemy:` instead, they mix with those defaults and migrations use the default SQLite URL instead of yours.

### `your_core_lib.py`

```python
from omegaconf import DictConfig

from core_lib.core_lib import CoreLib

from your_core_lib.data_layers.data_access.user_data_access import UserDataAccess
from your_core_lib.data_layers.service.user_service import UserService


class YourCoreLib(CoreLib):
    def __init__(self, config: DictConfig):
        super().__init__()
        self.config = config
        db = CoreLib.connection_factory_registry.get_or_reg(self.config.core_lib.data.sqlalchemy)
        self.user = UserService(UserDataAccess(db))
```

`get_or_reg` builds the factory once per process and shares it with any other Core-Lib that uses the same `_instance_key_` (see [Connection](connection.html#sharing-a-connection-between-core-libs)). Don't build this block with `instantiate_config`: it passes `_instance_key_` on to the factory as an argument, and the factory rejects it. When your config composes the packaged defaults, they add that key even if your YAML leaves it out.

### `user_data_access.py`

The [CRUD base classes](crud.html) already implement `get`, `create`, `update` and `delete` with `with self._db.get() as session:`. Write the same pattern yourself for any other query:

```python
from core_lib.connection.sql_alchemy_connection_factory import SqlAlchemyConnectionFactory
from core_lib.data_layers.data_access.db.crud.crud_data_access import CRUDDataAccess

from your_core_lib.data_layers.data.db.entities.user import User


class UserDataAccess(CRUDDataAccess):

    def __init__(self, db: SqlAlchemyConnectionFactory):
        super().__init__(User, db)

    def get_by_email(self, email: str) -> User:
        with self._db.get() as session:
            return session.query(User).filter(User.email == email).first()
```

## What happens in `with db.get() as session:`

1. `db.get()` creates a new `sqlalchemy.orm.Session` on the factory's engine. Always use it in a `with` statement: the commit and close happen only when the block exits.
2. Your code runs.
3. If your code raised, the error is logged and the session is rolled back.
4. The session is committed, flushed and closed. If your code raised, the exception then reaches your caller as usual.

Objects you return from the block keep their loaded values after the session closes, because the session is created with `expire_on_commit=False`. That is why `get_by_email` above can return the `User`.

The commit happens when the block exits. So a database error that appears only at commit, such as a unique-constraint violation on a row you added, is raised by the `with` statement itself. SQLAlchemy discards the failed transaction, but Core-Lib does not call `rollback()` or `close()` on the session, so it keeps its pooled connection until it is garbage-collected. If you need to handle such errors, call `session.flush()` inside the block. The error is then raised inside the block; let it leave the block, and the session is rolled back as in step 3, so catch it outside the `with`. If you catch it inside the block, call `session.rollback()` before the block ends, or the commit on exit raises `PendingRollbackError`.

## Config keys

These are the keys the factory reads from the `config:` node.

| Key | If you leave it out | What it does |
|---|---|---|
| `url` | required | `protocol`, `username`, `password`, `host`, `port`, `file`, joined by `build_url` (see [Connection](connection.html#how-a-connection-is-configured)). `file` is the database name, or for SQLite a file path relative to the working directory (`build_url` strips a leading `/`, so absolute paths do not work; `:memory:` does). |
| `log_queries` | `false` | Passed to `create_engine(echo=...)`: log every SQL statement. |
| `create_db` | **`true`** | Runs `Base.metadata.create_all()` when the factory is built, creating any missing tables. Core-Lib's packaged defaults set it to `false`; use migrations in production. |
| `session.pool_recycle` | `3200` | Seconds before a pooled connection is replaced. |
| `session.pool_pre_ping` | `false` | Test each pooled connection before using it. |
| `session.pool_size` | `5` | Size of the connection pool. Ignored for `sqlite`, `firebird`, `sybase`, `ibm_db_sa` and `redshift`. |
| `session.max_overflow` | `10` | Extra connections allowed beyond `pool_size`. Ignored for the same protocols. |

"If you leave it out" is the value in the code. If your config composes Core-Lib's packaged defaults (`defaults: - core_lib`), the keys you leave out take the packaged values instead, for example `create_db: false` and `pool_recycle: 3600`.

## SqlAlchemyConnection

*core_lib.connection.sql_alchemy_connection.SqlAlchemyConnection* [[source]](https://github.com/shay-te/core-lib/blob/master/core_lib/connection/sql_alchemy_connection.py){:target="_blank"}

Holds one `sqlalchemy.orm.Session` and returns it from `__enter__`. On `__exit__` it rolls the session back if the block raised, then calls `on_exit` (see [What happens](#what-happens-in-with-dbget-as-session) above).

```python
class SqlAlchemyConnection(Connection):
    def __init__(self, engine, on_exit):
```

**Arguments**

- **`engine`**: The `sqlalchemy.engine.Engine` to bind the session to.
- **`on_exit`**: Called with this connection when the `with` block exits. The factory passes a callback that calls `close()`.
