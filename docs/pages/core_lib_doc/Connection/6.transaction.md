`@Transaction()` runs a Service method as **one transaction**: every DataAccess call inside it shares one connection per connection factory, committed once when the method returns and rolled back when it raises. It works at the connection level, the same way for every connection type, so DataAccess code does not change.

*core_lib.connection.transaction_decorator.Transaction* [[source]](https://github.com/shay-te/core-lib/blob/master/core_lib/connection/transaction_decorator.py){:target="_blank"}

## Usage

Mark the Service method. `@Transaction()` goes **innermost**, under `@DuplicateErrorHandler()` and `@Cache(..., invalidate=True)`:

```python
from core_lib.cache.cache_decorator import Cache
from core_lib.connection.transaction_decorator import Transaction
from core_lib.data_layers.service.service import Service
from core_lib.error_handling.duplicate_error_decorator import DuplicateErrorHandler

CACHE_KEY_GROUP = 'widget_group_{group_id}'


class WidgetService(Service):

    def __init__(self, widget_data_access: WidgetDataAccess):
        self._widget_data_access = widget_data_access

    @Cache(CACHE_KEY_GROUP, handler_name=WIDGET_CACHE, invalidate=True)
    @DuplicateErrorHandler()
    @Transaction()
    def replace_group(self, group_id: int, names: list) -> list:
        self._widget_data_access.delete_group(group_id)
        for name in names:
            self._widget_data_access.create({Widget.group_id.key: group_id, Widget.name.key: name})
        return self.list_group(group_id)

    @Cache(CACHE_KEY_GROUP, handler_name=WIDGET_CACHE)
    def list_group(self, group_id: int) -> list:
        return self._widget_data_access.names_in_group(group_id)
```

The DataAccess is written exactly as outside a transaction — no `session` parameter, no `transaction()` or `*_in_transaction` methods:

```python
class WidgetDataAccess(CRUDDataAccess):

    def delete_group(self, group_id: int):
        with self._db.get() as session:
            return session.query(Widget).filter(Widget.group_id == group_id).delete()
```

- Each `with self._db.get()` block ends with a flush, so `create` returns the row with its id set and a child row can use it at once.
- Every DataAccess on the same database joins the same session, a DataAccess of another library included: the registry gives every library the same factory object.
- A row lock is an ordinary DataAccess read (`session.get(Entity, id, with_for_update=True)`) called inside the transaction; it is held until the commit. `FOR UPDATE` does nothing on sqlite.
- Only a plain `def` can be decorated. `async def`, generator and async-generator functions are refused when decorated, with `ValueError`: each returns before its body runs, so the transaction would end before any work happened.

## How it works

1. **Which transaction am I in?** A `contextvars.ContextVar` works like a sticky note that belongs to the running thread (or asyncio task). `@Transaction()` sticks a `TransactionScope` on the note when the method starts and takes it off when the method ends. A scope is just `{factory: connection}` plus a list of after-commit callbacks. Each thread has its own note, so two concurrent requests never see each other's scope.
2. **Same connection or a new one?** Every factory's `get()` is wrapped by the `ConnectionFactory` base class, and the wrapper reads the note first:
   - **No scope:** it runs the factory's own `get()`, a new connection each time, as before.
   - **A scope, and this factory is not in it yet:** it creates one connection, stores it in the scope and returns it wrapped.
   - **A scope, and this factory is already in it:** it returns the **same** stored connection, wrapped.
3. **Why doesn't each block commit?** Inside a scope `get()` returns a `JoinedConnection` wrapper. When the DataAccess block ends, Python calls the wrapper's `__exit__`, which only calls `connection.flush()`: the SQL is sent, ids are assigned, and a duplicate raises at that call. There is no commit and no close.
4. **Who calls `SqlAlchemyConnection.__exit__` now?** Nothing overrides it. Outside a transaction, Python's `with` calls it at the end of each block. Inside a transaction the scope calls it **once**, at the end: with `(None, None, None)` on success, which commits and closes, or with the exception on failure, which rolls back and closes.
5. **Nested `@Transaction()`** (Service A calls Service B, both decorated, on the same thread): B finds a scope already on the note and simply runs inside it. Only A's end commits.
6. **Threads.** The scope remembers the thread that opened it, and only that thread may join it. A worker thread gets its own connection and commits on its own (see Threads below).
7. **Atomicity depends on the backend.** The scope never touches SQL; it only postpones each connection's own `__exit__` (see the table below).

## Flow walkthroughs

Success:

```
replace_group() starts       -> @Transaction puts scope {} on this thread
    delete_group()             -> factory.get(): factory not in scope -> new session S1, stored
                                  DELETE on S1, block ends -> flush, NO commit
    create(row1)               -> factory.get(): factory in scope -> S1 again -> INSERT, flush (id set)
    create(row2)               -> S1 again -> INSERT, flush (id set)
    list_group()               -> @Cache sees the scope -> skips the cache; SELECT on S1 sees row1, row2
replace_group() returned     -> scope ends -> SqlAlchemyConnection.__exit__(None, None, None) -> ONE COMMIT + close
                                @Cache(invalidate=True), outside the transaction -> cache key deleted
```

Failure:

```
replace_group() starts       -> @Transaction puts scope {} on this thread
    delete_group()             -> factory.get(): factory not in scope -> new session S1, stored
                                  DELETE on S1, block ends -> flush, NO commit
    create(row1)               -> factory.get(): factory in scope -> S1 again -> INSERT, flush (id set)
    create(row2)               -> S1 again -> INSERT fails -> IntegrityError
replace_group() raised       -> scope ends -> SqlAlchemyConnection.__exit__(IntegrityError) -> rollback + close
                                DELETE and row1 undone; @DuplicateErrorHandler -> 409; cache key kept
```

Nested services:

```
WidgetService.move_widget() starts  -> @Transaction puts scope {} on this thread
    update(widget)                    -> new session S1, stored; UPDATE, flush
    GroupService.add_member()         -> also @Transaction(): a scope is already open -> runs inside it
        create(member)                -> same database, same factory -> S1 again; INSERT, flush
    add_member() returned             -> inner end: nothing committed
move_widget() returned              -> outer end: ONE COMMIT for both writes
                                       (had move_widget() raised after add_member(), both would roll back)
```

## Atomicity per backend

| Connection | What the transaction's end does | Rolled back on failure? |
|---|---|---|
| SQLAlchemy | commits or rolls back the one session, then closes it | yes |
| Neo4j | closes its one session; each `run` already auto-committed | no |
| MongoDB | nothing (its `__exit__` is a no-op) | no |
| Solr | nothing (its `__exit__` is a no-op) | no |
| Elasticsearch | nothing (its `__exit__` is a no-op) | no |
| Object | calls `close_session_callback` once | no |

Several factories in one transaction are each atomic on their own, but **not across factories**: there is no two-phase commit. Connections are ended in the order they joined; if one commit fails, the ones after it are rolled back with that error, while the ones before it stay committed.

## Errors

- The original exception propagates unchanged. A connection whose rollback fails is logged, and the others are still rolled back.
- A database error swallowed inside the transaction still fails it: the session's flush failed, so the commit raises `PendingRollbackError`, nothing is saved, and the session is closed. A swallowed error that is not from the database (a 404, a `ValueError`) lets the transaction commit. There is no "rollback-only" marking.
- If a commit fails, the after-commit callbacks (deferred cache deletes) do not run.

## One session: what changes

- While a loaded entity is still referenced, `get()` returns that same object without reading the database again. A raw SQL update, a bulk update with `synchronize_session=False`, or another thread's commit is invisible to it; a column query still sees it.
- Changing an attribute of an entity a DataAccess returned is saved at the next flush. Outside a transaction the session is already closed and the change is lost.
- A second factory on the same database is a second connection. On sqlite it waits on the first one's write lock until it fails with `database is locked`; on Postgres it can block on the first one's row locks.
- A write on another thread outside the transaction commits on its own and survives the transaction's rollback; on sqlite it waits for the transaction's write lock first.

## Threads

- A scope is joined only from the thread that opened it.
- Concurrent transactions on different threads are isolated: each has its own scope and its own connection, uncommitted rows of one are invisible to the other, and a rollback in one never touches another.
- `asyncio.to_thread`, and `threading.Thread` from Python 3.14, copy the ContextVar into a worker thread. The worker still does not join the scope, because one SQLAlchemy `Session` is not safe across threads: it gets its own connection and commits on its own. A worker may open its own `@Transaction()`.
- A sync `@Transaction()` function called from inside a running asyncio event loop works as anywhere else.

## `@Cache` inside a transaction

- A cached read **bypasses the cache entirely**: no read (the cache may hold the row as it was before this transaction's writes) and no fill (the rows are not committed yet and may be rolled back).
- `invalidate=True` **waits for the commit** and is dropped on rollback. If one deferred delete fails, it raises after the commit and the remaining deletes still run.
- Outside a transaction, and in a worker thread, `@Cache` behaves exactly as before.

## Writing a connection factory

Nothing to add: a factory's `get()` is wrapped by the base class, so any factory, in any library, joins an open transaction. `Connection.flush()` is a no-op; a backend that buffers writes overrides it.
