In the [Hello, World](/index.html#a-complete-core-lib-app-in-one-file) you saw three classes wired in a chain: `UserService` → `UserDataAccess` → `Connection`. This page covers the conventions for filling those three with real code.

The three sit in three subfolders under `data_layers/`:

```text
data_layers/
├── data/         ← entity definitions (ORM models, mixins)
├── data_access/  ← query classes
└── service/      ← business logic
```

> `Client`, `Job`, and `Cache` live alongside `data_layers/` in your project, not inside it. See [Project Structure](/project_structure.html).

---

## 1. The entity (ORM model)

An entity is a Python class that maps to one database table. Put it in `data_layers/data/db/`.

```python
# data_layers/data/db/user.py
from sqlalchemy import Column, Integer, VARCHAR
from core_lib.data_layers.data.db.sqlalchemy.base import Base


class User(Base):
    __tablename__ = 'user'
    id = Column(Integer, primary_key=True)
    email = Column(VARCHAR(255), nullable=False)
```

Optionally inherit `SoftDeleteMixin` to get automatic `created_at` / `updated_at` / `deleted_at` columns — see [Soft Delete Handler](/soft_delete.html). The mixin must come **before** `Base` in the inheritance order so its methods take precedence.

```python
class User(SoftDeleteMixin, Base):
    ...
```

## 2. `DataAccess` — the query layer

A `DataAccess` class wraps one entity and exposes the queries your application needs. It only talks to the database — never to business logic or web requests.

```python
# data_layers/data_access/user_data_access.py
from core_lib.connection.sql_alchemy_connection_factory import SqlAlchemyConnectionFactory
from core_lib.data_layers.data_access.data_access import DataAccess
from your_core_lib.data_layers.data.db.user import User


class UserDataAccess(DataAccess):
    def __init__(self, db: SqlAlchemyConnectionFactory):
        self._db = db

    def get(self, user_id: int):
        with self._db.get() as session:
            return session.query(User).get(user_id)
```

For the common CRUD pattern (`get`, `create`, `update`, `delete`), extend [`CRUDDataAccess`](/crud.html) instead of writing them by hand.

---

## 3. `Service` — the business logic layer

A `Service` composes one or more `DataAccess` (and `Client`) instances and runs business logic on top of them. It's the API your route handlers, jobs, and tests call.

```python
# data_layers/service/user_service.py
from core_lib.cache.cache_decorator import Cache
from core_lib.data_layers.service.service import Service
from core_lib.data_transform.result_to_dict import ResultToDict
from your_core_lib.data_layers.data_access.user_data_access import UserDataAccess

CACHE_KEY_USER = 'user_{user_id}'


class UserService(Service):
    def __init__(self, user_da: UserDataAccess):
        self.user_da = user_da

    @Cache(CACHE_KEY_USER)
    @ResultToDict()
    def get(self, user_id: int):
        return self.user_da.get(user_id)
```

The two decorators are optional:

- `@Cache` reads from the registered `CacheHandler` — see [Cache](/cache.html).
- `@ResultToDict` converts the returned ORM object into a plain dict — see [Result to Dict](/result_to_dict.html).

---

## Why this separation matters

- **Entity** changes (rename a column, add a field) only touch `data/`.
- **Query** changes (new filter, new index hint, pagination) only touch `data_access/`.
- **Business rule** changes only touch `service/`.

If you find yourself editing all three for one feature, that's normal. If you find yourself editing the wrong one — business logic creeping into `data_access/`, or raw queries showing up in `service/` — the boundary is leaking.
