The [one-file example](index.html#a-complete-core-lib-app-in-one-file) on the home page wires a chain: `UserService` → `UserDataAccess` → `SqlAlchemyConnectionFactory`. This page shows what goes in each layer of a real project: the entity, the `DataAccess` that queries it, and the `Service` that holds the business rules. Unfamiliar with terms like "entity", "ORM", or "session"? See the [Glossary](glossary.html).

> **Where it fits:** Service + DataAccess layers. Entities define stored data, `DataAccess` owns queries, and `Service` owns business logic.

The three sit in three subfolders under `data_layers/`:

```text
data_layers/
├── data/         ← entity definitions (ORM models, mixins)
├── data_access/  ← query classes
└── service/      ← business logic
```

> `Client` and `Job` classes live in their own folders next to `data_layers/`, not inside it. See [Project Structure](project_structure.html).

---

## 1. The entity (ORM model)

An entity is a Python class that maps to one database table. Put it in `data_layers/data/db/entities/` (see [Project Structure](project_structure.html)).

```python
# your_core_lib/data_layers/data/db/entities/user.py
from sqlalchemy import Column, Integer, VARCHAR
from core_lib.data_layers.data.db.sqlalchemy.base import Base


class User(Base):
    __tablename__ = 'user'
    id = Column(Integer, primary_key=True)
    email = Column(VARCHAR(255), nullable=False)
```

Optionally inherit `SoftDeleteMixin` to add `created_at` / `updated_at` / `deleted_at` columns — see [Soft Delete Handler](soft_delete.html).

```python
class User(Base, SoftDeleteMixin):
    ...
```

## 2. `DataAccess` — the query layer

A `DataAccess` class wraps one entity and exposes the queries your application needs. It talks to the database and nothing else: no business rules, no web requests.

```python
# your_core_lib/data_layers/data_access/user_data_access.py
from core_lib.connection.sql_alchemy_connection_factory import SqlAlchemyConnectionFactory
from core_lib.data_layers.data_access.db.crud.crud_data_access import CRUDDataAccess
from your_core_lib.data_layers.data.db.entities.user import User


class UserDataAccess(CRUDDataAccess):
    def __init__(self, db: SqlAlchemyConnectionFactory):
        super().__init__(User, db)        # adds get, create, update and delete

    def get_by_email(self, email: str):   # a query the base class does not have
        with self._db.get() as session:
            return session.query(User).filter(User.email == email).first()
```

[`CRUDDataAccess`](crud.html) supplies `get`, `create`, `update` and `delete`, so you write only the extra queries. Two more things that belong in this layer, both handled by Core-Lib:

- **Validating input.** Pass a [RuleValidator](rules_validator.html) as the third argument, `super().__init__(User, db, rule_validator)`. `create()` and `update()` check every incoming dict against it.
- **Not found.** `get()` raises `StatusCodeException` with status 404 when no row matches, through `@NotFoundErrorHandler()` (see [Error Handlers](error_handler.html)).

For joins that the caller chooses at run time, see [JoinConfig](join_config.html).

## 3. `Service` — the business logic layer

A `Service` holds the business rules. It calls one or more `DataAccess` (and `Client`) objects for data, and it is the API your route handlers, jobs and tests call.

```python
# your_core_lib/data_layers/service/user_service.py
from http import HTTPStatus

from core_lib.cache.cache_decorator import Cache
from core_lib.data_layers.service.service import Service
from core_lib.data_transform.result_to_dict import ResultToDict
from core_lib.error_handling.status_code_exception import StatusCodeException
from your_core_lib.data_layers.data.db.entities.user import User
from your_core_lib.data_layers.data_access.user_data_access import UserDataAccess

CACHE_KEY_USER = 'user_{user_id}'


class UserService(Service):
    def __init__(self, user_data_access: UserDataAccess):
        self._user_data_access = user_data_access

    @ResultToDict()
    def sign_up(self, email: str) -> dict:
        email = email.strip().lower()     # rule 1: emails are stored lower-case
        if self._user_data_access.get_by_email(email):   # rule 2: one account per email
            raise StatusCodeException(HTTPStatus.CONFLICT, f'{email} is already registered')
        return self._user_data_access.create({User.email.key: email})

    @Cache(CACHE_KEY_USER)
    @ResultToDict()
    def get(self, user_id: int) -> dict:
        return self._user_data_access.get(user_id)
```

`sign_up('  Jane@Example.com ')` returns `{'id': 1, 'email': 'jane@example.com'}`. Calling it again with the same email raises `StatusCodeException` with status 409. The two rules live only here: the route that calls `sign_up` does not repeat them, and `UserDataAccess` runs the queries without knowing why.

The two decorators are optional:

- `@Cache` stores the result in a `CacheHandler` registered on `CoreLib.cache_registry`, so a second `get(1)` does not query the database. With no handler registered, the call raises `ValueError`. See [Cache](cache.html).
- `@ResultToDict` converts the returned ORM object into a plain dict. See [Result to Dict](result_to_dict.html).

---

## Why this separation matters

- **Entity** changes (a new column, a new table) go in `data/`.
- **Query** changes (a new filter, pagination) go in `data_access/`.
- **Business rule** changes go in `service/`.

If you find yourself editing all three for one feature, that's normal. If you find yourself editing the wrong one — business logic creeping into `data_access/`, or raw queries showing up in `service/` — the boundary is leaking.
