Writing `get`, `create`, `update`, and `delete` against every SQLAlchemy model is tedious and identical every time. Core-Lib provides three `CRUD` base classes — pick the one that matches how you want deletes to behave, then your `DataAccess` only defines what makes it different.

> **Where it fits:** DataAccess layer. Use these base classes when a SQLAlchemy entity needs normal CRUD methods and your `Service` should not write queries directly.

| Base class | Entity needs | `delete(id)` | Use when |
|---|---|---|---|
| `CRUDDataAccess` | nothing extra | removes the row | Deleted rows don't need to be kept |
| `CRUDSoftDeleteDataAccess` | `SoftDeleteMixin` | sets `deleted_at`; the row stays | You want to keep deleted rows |
| `CRUDSoftDeleteWithTokenDataAccess` | `SoftDeleteMixin` + `SoftDeleteTokenMixin` | sets `deleted_at` and `deleted_at_token`; the row stays | You keep deleted rows **and** need a unique constraint that ignores them |

All three share `create()` and `update()`. Every `get()` raises `StatusCodeException` with status 404 when no row matches, and the two soft-delete classes treat a deleted row as missing (details in the [Reference](#get-and-delete)).

## Example — plain CRUD

```python
from sqlalchemy import Column, Integer, VARCHAR, Boolean
from core_lib.connection.sql_alchemy_connection_factory import SqlAlchemyConnectionFactory
from core_lib.data_layers.data.db.sqlalchemy.base import Base
from core_lib.data_layers.data_access.db.crud.crud_data_access import CRUDDataAccess


class Customer(Base):
    __tablename__ = 'customer'
    id = Column(Integer, primary_key=True)
    name = Column(VARCHAR(255), nullable=False)
    email = Column(VARCHAR(255), nullable=False)
    active = Column(Boolean, nullable=False)


class CustomerDataAccess(CRUDDataAccess):
    def __init__(self, db: SqlAlchemyConnectionFactory):
        super().__init__(Customer, db)
```

That's the whole `DataAccess`. `get`, `create`, `update`, and `delete` come from the base class (`db` is a `SqlAlchemyConnectionFactory`, see [SQLAlchemy Connection Factory](sql_alchemy_connection.html)):

```python
customer_data_access = CustomerDataAccess(db)
customer = customer_data_access.create({
    Customer.name.key: 'Jon Doe',
    Customer.email.key: 'jon@doe.com',
    Customer.active.key: True,
})
customer_data_access.update(customer.id, {Customer.email.key: 'jon.doe@example.com'})
customer_data_access.get(customer.id)       # the Customer row, email 'jon.doe@example.com'
customer_data_access.delete(customer.id)    # returns 1; the row is gone
customer_data_access.get(customer.id)       # raises StatusCodeException (404)
```

`Customer.name.key` is the column name, `'name'`. If the column is renamed, `Customer.name` raises `AttributeError` right away, while `create()` silently skips a string key that no longer matches an attribute.

## Example — soft delete, with a RuleValidator

Same columns. The entity adds `SoftDeleteMixin`, the `DataAccess` extends a different base class, and this time it passes a [RuleValidator](rules_validator.html) that `create()` and `update()` run on every incoming dict:

```python
from core_lib.data_layers.data.db.sqlalchemy.mixins.soft_delete_mixin import SoftDeleteMixin
from core_lib.data_layers.data_access.db.crud.crud_soft_data_access import CRUDSoftDeleteDataAccess
from core_lib.rule_validator.rule_validator import RuleValidator, ValueRuleValidator


class Customer(Base, SoftDeleteMixin):                 # adds created_at, updated_at, deleted_at
    __tablename__ = 'customer'
    id = Column(Integer, primary_key=True)
    name = Column(VARCHAR(255), nullable=False)
    email = Column(VARCHAR(255), nullable=False)
    active = Column(Boolean, nullable=False)


customer_rule_validator = RuleValidator([
    ValueRuleValidator(Customer.name.key, str),
    ValueRuleValidator(Customer.email.key, str, custom_validator=lambda email: '@' in email),
    ValueRuleValidator(Customer.active.key, bool),
])


class CustomerDataAccess(CRUDSoftDeleteDataAccess):    # different base class
    def __init__(self, db: SqlAlchemyConnectionFactory):
        super().__init__(Customer, db, customer_rule_validator)
```

```python
# customer_data_access and customer are created as in the plain example
customer_data_access.update(customer.id, {Customer.email.key: 'not-an-email'})  # PermissionError
customer_data_access.update(customer.id, {'nickname': 'JD'})  # PermissionError: no rule for `nickname`
customer_data_access.delete(customer.id)  # returns 1; sets deleted_at, the row stays
customer_data_access.get(customer.id)     # raises StatusCodeException (404)
```

The two write methods validate differently:

- `update()` is strict: a key with no rule raises `PermissionError`.
- `create()` is not strict: a key with no rule is not checked. `create()` then sets only keys that are attributes of the entity, so an unknown key is silently ignored, and so is `id`.

`update()` does not check `deleted_at`, so it also changes a soft-deleted row.

## Example — soft delete with token

The entity adds `SoftDeleteTokenMixin` as well, which adds an integer `deleted_at_token` column. It is `0` while the row is live. `delete()` sets it to `int(datetime.utcnow().timestamp())`, a number of seconds, so every deleted row gets a non-zero value. That makes a unique constraint that ignores deleted rows possible:

```python
from sqlalchemy import UniqueConstraint
from core_lib.data_layers.data.db.sqlalchemy.mixins.soft_delete_mixin import SoftDeleteMixin
from core_lib.data_layers.data.db.sqlalchemy.mixins.soft_delete_token_mixin import SoftDeleteTokenMixin
from core_lib.data_layers.data_access.db.crud.crud_soft_delete_token_data_access import CRUDSoftDeleteWithTokenDataAccess


class Customer(Base, SoftDeleteMixin, SoftDeleteTokenMixin):   # + deleted_at_token
    __tablename__ = 'customer'
    id = Column(Integer, primary_key=True)
    name = Column(VARCHAR(255), nullable=False)
    email = Column(VARCHAR(255), nullable=False)
    active = Column(Boolean, nullable=False)

    __table_args__ = (UniqueConstraint('email', 'deleted_at_token'),)   # one live row per email


class CustomerDataAccess(CRUDSoftDeleteWithTokenDataAccess):   # different base class
    def __init__(self, db: SqlAlchemyConnectionFactory):
        super().__init__(Customer, db)
```

Creating a second live customer with the same email raises `IntegrityError`. After `delete()`, the old row has a non-zero token, so a new customer with that email can be created. `SoftDeleteTokenMixin` does not create an index; add one in your migration if you query on `deleted_at_token`.

## Reference

### CRUD

*core_lib.data_layers.data_access.db.crud.crud.CRUD* [[source]](https://github.com/shay-te/core-lib/blob/master/core_lib/data_layers/data_access/db/crud/crud.py#L7){:target="_blank"}

The abstract base class of all three. It implements `create()` and `update()`; each subclass implements `get()` and `delete()`. The three subclasses take the same constructor arguments:

```python
class CRUD(ABC):
    def __init__(self, db_entity, db: SqlAlchemyConnectionFactory, rule_validator: RuleValidator = None):
```

**Arguments**

- **`db_entity`**: The SQLAlchemy entity class this `DataAccess` reads and writes.
- **`db`** *`(SqlAlchemyConnectionFactory)`*: The connection factory that opens a session for each call.
- **`rule_validator`** *`(RuleValidator)`*: Optional. Validates the dicts passed to `create()` and `update()`. See [Rules Validator](rules_validator.html).

### create()

*core_lib.data_layers.data_access.db.crud.crud.CRUD.create()* [[source]](https://github.com/shay-te/core-lib/blob/master/core_lib/data_layers/data_access/db/crud/crud.py#L23){:target="_blank"}

Inserts one row and returns the new entity, with its `id` set.

```python
def create(self, data: dict):
```

**Arguments**

- **`data`** *`(dict)`*: Column name to value, for example `{Customer.name.key: 'Jon Doe'}`. Must not be empty. Runs `rule_validator.validate_dict(data, strict_mode=False)` first when a validator is set. Keys that are not attributes of the entity, and `id`, are ignored.

### update()

*core_lib.data_layers.data_access.db.crud.crud.CRUD.update()* [[source]](https://github.com/shay-te/core-lib/blob/master/core_lib/data_layers/data_access/db/crud/crud.py#L17){:target="_blank"}

Updates the row with the given primary key. Returns `None`. It does not filter out soft-deleted rows.

```python
def update(self, id: int, data: dict):
```

**Arguments**

- **`id`** *`(int)`*: Primary key of the row to update.
- **`data`** *`(dict)`*: Column name to new value. Must not be empty. Runs `rule_validator.validate_dict(data)` first when a validator is set, which raises `PermissionError` for a key with no rule.

### get() and delete()

```python
def get(self, id: int):
def delete(self, id: int):
```

- **`id`** *`(int)`*: Primary key of the row.

`get()` returns the entity, or raises `StatusCodeException` with status 404 (through `@NotFoundErrorHandler()`) when no row matches. `delete()` returns the number of rows it changed: `0` when no row has that primary key.

| Class | `get(id)` finds a row only if | `delete(id)` |
|---|---|---|
| `CRUDDataAccess` | it exists | Removes the row. |
| `CRUDSoftDeleteDataAccess` | `deleted_at` is `NULL` | Sets `deleted_at` to `datetime.utcnow()`. |
| `CRUDSoftDeleteWithTokenDataAccess` | `deleted_at_token` is `0` (it does not look at `deleted_at`) | Sets `deleted_at` to `datetime.utcnow()` and `deleted_at_token` to `int(datetime.utcnow().timestamp())`, in seconds. |
