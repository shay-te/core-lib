`JoinConfig` is a declarative description of a SQL join (or computed column) that a `Data Access` layer can apply to a SQLAlchemy query. It lets callers pass dynamic joins through a service interface without coupling the data-access layer to any specific entity.

It lives in `core_lib.data_layers.data.db.join_config` and is split across two files:

- `join_config.py` — the `JoinConfig` dataclass.
- `apply_join_configs.py` — `apply_join_configs(query, joins)`, the canonical iteration loop that every consumer calls.

## The `JoinConfig` dataclass

```python
from dataclasses import dataclass
from typing import Any


@dataclass
class JoinConfig:
    columns: list                   # column expressions added to the SELECT
    model: Any = None               # SQLAlchemy entity class (JOIN mode)
    join_condition: Any = None      # ON clause (JOIN mode)
    condition: Any = None           # extra ON clause, AND-ed onto join_condition
    is_outer_join: bool = False     # True → LEFT OUTER JOIN; False → INNER JOIN
```

### Two modes

**JOIN mode** — set `model` + `join_condition`. The data-access layer runs:

```sql
SELECT <base columns>, <jc.columns>
FROM <base entity>
{JOIN | LEFT OUTER JOIN} <jc.model>
  ON <jc.join_condition> [AND <jc.condition>]
```

**COLUMN-ONLY mode** — leave `model` and `join_condition` as `None`. The data-access layer only adds `jc.columns` to the SELECT without performing any JOIN. Useful for correlated scalar subqueries and aggregated JSON-array columns (e.g. `json_agg(...)` against a related table referenced by IDs inside a JSON column).

### Column aliasing

Every column you put on `JoinConfig.columns` should carry a `.label('...')` so `result_to_dict` produces a stable, collision-free key:

```python
JoinConfig(
    model=CustomField,
    join_condition=FormPageField.target_field_id == CustomField.id,
    columns=[
        CustomField.label.label('custom_field_label'),
        CustomField.id.label('custom_field_id'),
    ],
    is_outer_join=True,
)
```

Two joined tables with same-named columns would otherwise silently overwrite each other in the result dict.

## The `apply_join_configs` helper

```python
def apply_join_configs(query, joins):
    """Apply a list of JoinConfig objects to an existing SQLAlchemy query."""
    for join_config in joins or []:
        if not isinstance(join_config, JoinConfig):
            continue
        if join_config.columns:
            query = query.add_columns(*join_config.columns)
        if join_config.model is None or join_config.join_condition is None:
            continue
        effective_condition = (
            and_(join_config.join_condition, join_config.condition)
            if join_config.condition is not None
            else join_config.join_condition
        )
        if join_config.is_outer_join:
            query = query.outerjoin(join_config.model, effective_condition)
        else:
            query = query.join(join_config.model, effective_condition)
    return query
```

Non-`JoinConfig` items in `joins` are silently skipped, so callers can interleave Nones / placeholders without guarding upstream.

## Typical Data Access pattern

```python
from core_lib.data_layers.data.db.join_config import apply_join_configs


class MyEntityDataAccess(CRUDSoftDeleteWithTokenDataAccess):
    def all(self, owner_id: int, joins: list = None):
        with self._db.get() as session:
            base = (
                session.query(*list(MyEntity.__table__.columns))
                if joins
                else session.query(MyEntity)
            )
            query = apply_join_configs(base, joins)
            return query.filter(MyEntity.owner_id == owner_id).all()
```

The caller (typically a service layer) builds the `JoinConfig` list and passes it in:

```python
class MyService:
    def all(self, owner_id: int):
        joins = [
            JoinConfig(
                model=OtherEntity,
                join_condition=MyEntity.other_id == OtherEntity.id,
                columns=[OtherEntity.label.label('other_label')],
                is_outer_join=False,
            ),
        ]
        return self._data_access.all(owner_id, joins=joins)
```

## When to use COLUMN-ONLY mode

When the data you need isn't a simple FK join — typically when an ID list is stored inside a JSON column and you want to aggregate the related rows into a single JSON array column on each result row. Postgres example:

```python
target_id_subq = (
    select(cast(
        func.json_array_elements_text(MyEntity.meta_data['related_ids']),
        Integer,
    ))
    .scalar_subquery()
)

target_users_expr = func.coalesce(
    select(func.json_agg(func.json_build_object(
        'id', User.id,
        'first_name', User.first_name,
    )))
    .where(User.id.in_(target_id_subq))
    .correlate(MyEntity)
    .scalar_subquery(),
    cast('[]', JSON),
).label('target_users')

JoinConfig(columns=[target_users_expr])  # column-only: no JOIN, no row explosion
```

One row per `MyEntity`, `target_users` arrives as a JSON array. Single SQL statement.
