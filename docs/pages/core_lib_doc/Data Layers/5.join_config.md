`JoinConfig` describes a SQL join (or an extra computed column) as data, so a `Service` can decide which joins a query needs and pass them to a `DataAccess` method. The `DataAccess` applies whatever it is given with `apply_join_configs`, without knowing the joined entities in advance.

> **Where it fits:** DataAccess layer, with the join choice made in the Service. Use it when one query needs different joins for different callers.

```python
from core_lib.data_layers.data.db.join_config import JoinConfig, apply_join_configs
```

The package has two files:

- `join_config.py`: the `JoinConfig` dataclass.
- `apply_join_configs.py`: `apply_join_configs(query, joins)`, which applies a list of `JoinConfig` to a query.

## The `JoinConfig` dataclass

```python
from dataclasses import dataclass
from typing import Any


@dataclass
class JoinConfig:
    columns: list                   # column expressions added to the SELECT
    model: Any = None               # SQLAlchemy entity class (JOIN mode)
    join_condition: Any = None      # ON clause (JOIN mode)
    condition: Any = None           # extra ON clause, AND-ed onto join_condition
    is_outer_join: bool = False     # True → LEFT OUTER JOIN; False → INNER JOIN
```

### Two modes

**JOIN mode**: set `model` and `join_condition`. `apply_join_configs` adds:

```sql
SELECT <base columns>, <jc.columns>
FROM <base entity>
{JOIN | LEFT OUTER JOIN} <jc.model>
  ON <jc.join_condition> [AND <jc.condition>]
```

`condition` goes into the `ON` clause, not into `WHERE`, so with `is_outer_join=True` a row that fails it is kept, with `NULL` in the joined columns.

**COLUMN-ONLY mode**: leave `model` and `join_condition` as `None`. Only `columns` is added to the SELECT, with no JOIN. Use it for correlated subqueries, such as aggregating related rows into one JSON array column (example [below](#when-to-use-column-only-mode)).

> If you set `model` but leave `join_condition` as `None`, no JOIN is added, but the columns still are. The query then selects from both tables with no condition (a cross join), so set both or neither.

### Label every column

The examples on this page use these two entities:

```python
from sqlalchemy import Column, Integer, VARCHAR, JSON
from core_lib.data_layers.data.db.sqlalchemy.base import Base


class User(Base):
    __tablename__ = 'user'
    id = Column(Integer, primary_key=True)
    first_name = Column(VARCHAR(255), nullable=False)


class Task(Base):
    __tablename__ = 'task'
    id = Column(Integer, primary_key=True)
    title = Column(VARCHAR(255), nullable=False)
    owner_id = Column(Integer, nullable=False)
    meta_data = Column(JSON)                     # e.g. {'related_ids': [1, 2]}
```

Give every column in `JoinConfig.columns` a `.label('...')`. `result_to_dict` builds each row's dict by column name, so two columns with the same name overwrite each other without an error. Joining `User` and adding `User.id` unlabeled turns task 10 into `{'id': 1, 'title': 'Write docs', ...}`: the user's `id` replaced the task's. With `User.id.label('owner_user_id')` the row keeps `'id': 10` and gains `'owner_user_id': 1`.

## The `apply_join_configs` helper

```python
def apply_join_configs(query, joins):
    """Apply a list of JoinConfig objects to an existing SQLAlchemy query."""
    for join_config in joins or []:
        if not isinstance(join_config, JoinConfig):
            continue
        if join_config.columns:
            query = query.add_columns(*join_config.columns)
        if join_config.model is None or join_config.join_condition is None:
            continue
        effective_condition = (
            and_(join_config.join_condition, join_config.condition)
            if join_config.condition is not None
            else join_config.join_condition
        )
        if join_config.is_outer_join:
            query = query.outerjoin(join_config.model, effective_condition)
        else:
            query = query.join(join_config.model, effective_condition)
    return query
```

Items in `joins` that are not a `JoinConfig` (for example `None`) are skipped, so callers can build the list with optional entries. `None` or an empty list returns the query unchanged.

## Typical Data Access pattern

```python
from core_lib.connection.sql_alchemy_connection_factory import SqlAlchemyConnectionFactory
from core_lib.data_layers.data.db.join_config import apply_join_configs
from core_lib.data_layers.data_access.db.crud.crud_data_access import CRUDDataAccess


class TaskDataAccess(CRUDDataAccess):
    def __init__(self, db: SqlAlchemyConnectionFactory):
        super().__init__(Task, db)

    def list_by_owner(self, owner_id: int, joins: list = None):
        with self._db.get() as session:
            base = (
                session.query(*Task.__table__.columns)   # plain columns, so joined columns can be added
                if joins
                else session.query(Task)
            )
            query = apply_join_configs(base, joins)
            return query.filter(Task.owner_id == owner_id).all()
```

With joins it returns `Row` objects; without, `Task` entities. `@ResultToDict()` turns both into dicts.

The caller, typically a `Service`, builds the `JoinConfig` list and passes it in:

```python
from core_lib.data_layers.data.db.join_config import JoinConfig
from core_lib.data_layers.service.service import Service
from core_lib.data_transform.result_to_dict import ResultToDict


class TaskService(Service):
    def __init__(self, task_data_access: TaskDataAccess):
        self._task_data_access = task_data_access

    @ResultToDict()
    def list_with_owner_name(self, owner_id: int) -> list:
        owner_join = JoinConfig(
            model=User,
            join_condition=Task.owner_id == User.id,
            columns=[User.first_name.label('owner_first_name')],
        )
        return self._task_data_access.list_by_owner(owner_id, joins=[owner_join])
```

With user 1 named Ada, `list_with_owner_name(1)` returns:

```python
[{'id': 10, 'title': 'Write docs', 'owner_id': 1, 'meta_data': {'related_ids': [1, 2]}, 'owner_first_name': 'Ada'}]
```

## When to use COLUMN-ONLY mode

When the related rows are not reachable with a plain foreign-key join. Here each task stores a list of user ids in its JSON column, and you want those users as one JSON array column on each task row. This example uses PostgreSQL functions (`json_array_elements_text`, `json_agg`, `json_build_object`, `json_build_array`):

```python
from sqlalchemy import Integer, cast, func, select

related_ids = (
    select(cast(func.json_array_elements_text(Task.meta_data['related_ids']), Integer))
    .correlate(Task)                 # read meta_data from the outer task row
    .scalar_subquery()
)

related_users = func.coalesce(
    select(func.json_agg(func.json_build_object('id', User.id, 'first_name', User.first_name)))
    .where(User.id.in_(related_ids))
    .correlate(Task)
    .scalar_subquery(),
    func.json_build_array(),         # [] when nothing matches
).label('related_users')

related_users_join = JoinConfig(columns=[related_users])   # COLUMN-ONLY: no model, no join_condition
```

Passed to `list_by_owner(1, joins=[related_users_join])`, it returns one row per task, in a single SQL statement:

```python
[{'id': 10, 'title': 'Write docs', 'owner_id': 1, 'meta_data': {'related_ids': [1, 2]},
  'related_users': [{'id': 1, 'first_name': 'Ada'}, {'id': 2, 'first_name': 'Grace'}]}]
```

Both `.correlate(Task)` calls matter. Without the one on `related_ids`, the innermost subquery gets its own `FROM task`, and every row receives the related users of all tasks.
